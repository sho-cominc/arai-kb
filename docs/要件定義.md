# 団体受注 管理・共有アプリ — 要件定義書 (ドラフト)

> 目的: ホテルの団体受注を、フロント・予約・セールス・料飲など**社内全体で確認・管理・進行・共有**するためのアプリ。
> 設計思想: **器(部署・ステータス・入力項目)はデータ駆動で汎用に作り、まず自社運用で磨く**。他ホテル・他場面への流用は将来展望とし、初期から汎用UIを作り込まない。
> 作成: このドキュメントは Sho の口頭要件をもとに構造化し、AIチーム(Yuri/Webber/Dev/Hana)のレビューを反映したもの。

---

## 0. コンセプト — 「1入力 → 多出力」

このアプリの本質は **1回の入力から、必要な複数の成果物を自動生成すること**。

```
        ┌─────────────────────────────────────────┐
        │   受注入力画面(分かりやすく・漏れなく)     │
        │   ↑ 自社の料金・部屋空き状況を参照しながら   │
        └─────────────────────────────────────────┘
                          │ 1回入力
   ┌──────────┬──────────┬──────────┬──────────┬──────────┐
   ▼          ▼          ▼          ▼          ▼          ▼
社内共有ページ  調理・発注書   見積書      イベント     会場手配     カレンダー
(全部署)     (料飲/厨房)  請求書       工程表      ・共有       (全成果物を
                        領収書                              日付で俯瞰)
   │          │          │          │          │          │
   └──────────┴──────────┴─── ワンクリックで PDF / 印刷 ───┴──────────┘
```

---

## 1. 機能要件

### 1-1. 入力画面(最重要)
- **分かりやすい入力画面**があり、必要な情報を**漏らさずに**入れられること。
- **セクション式1ページ+アンカーナビ**(ウィザード強制はしない。団体受注は順不同・後日追記が常態のため):
  ①案件基本 → ②宿泊 → ③食事 → ④宴会・会場 → ⑤送迎 → ⑥料金・支払 → ⑦その他
- **新規作成は3項目(案件名・日程・人数)だけで下書き保存可**。「全部入れないと保存できない」は作らない。
- **「漏れなく」は成果物別レディネスで実現する**(全項目一律必須にしない):
  出力単位で充足度を表示 — 例)「見積書 発行可 ✓ / 調理発注書 発行不可 ✗(アレルギー未入力)」。
  各セクション見出しにも充足バッジ(✓/残n件)。
- **選択式 vs 自由記述の使い分け(3原則)**:
  1. マスタに実体があるもの(会場・部屋タイプ・プラン・担当)→ **選択式**(重複判定・料金連動が機械処理できる)
  2. 成果物で計算・配置に使う値(人数・数量・時刻・金額)→ **構造化入力**(数値/日付/時刻)
  3. 帳票に印字されるだけの文言(特記・調整内容)→ **自由記述**
  - 横断ルール: **「選択で分類し、自由記述で補足する」**。融通が要る項目は 選択式+「その他」+補足メモ欄をペアで置く。
- **マスタ参照はインラインで**: 「見に行く」UIではなく「出てくる」UI(部屋タイプを選んだ瞬間、空室数と料金が選択肢に併記される)。モバイルで別画面参照は破綻するため。

### 1-2. 自社マスタ参照(入力を支援)
入力しながら、自社が持つデータを**すぐ確認できる**仕組み:
- **料金**(部屋・プラン・宴会・オプション等の料金表)
- **部屋の空き状況**
- ※ データ源は要決定(既存PMS〈Opera等〉連携 or アプリ内マスタ手入力)。→ 未決事項に記載。

### 1-3. 成果物の生成(入力から自動作成)
入力データをもとに、以下を作成できること。

| # | 成果物 | 主な利用者 | 用途 | 出力形式 |
|---|--------|-----------|------|---------|
| A | **社内共有ページ** | フロント / 予約 / セールス / 料飲 = 社内全体 | 案件の全体像を1画面で共有 | **Web画面(ライブ)** |
| B | **調理・発注書** | 料飲 / 厨房 / レストラン | 料理内容・数量・仕入の指示 | **Excel**(→印刷/PDF) |
| C | **見積書 / 請求書 / 領収書** | お客様向け | 金額提示・請求・受領証明 | **Excel**(→印刷/PDF・ロゴ入り) |
| D | **イベント工程表** | 運営・関係部署 | 当日のタイムライン・進行 | **Excel**(→印刷/PDF) |

> **全帳票(B・C・D)は Excel を単一の元とする。** Excel なら誰でも操作でき、印刷も PDF 化も Excel から一発。PDF を元にすると Excel 化できないため、元は必ず Excel に統一する。

### 1-4. カレンダー表示
- A〜D および案件そのものが**カレンダーで表示**され、**見落としがない**こと。
- 利用日・搬入日・イベント日・請求期日などを日付で俯瞰できる。

### 1-5. 会場手配・共有
- 施設内の**会場(宴会場・レストラン等)を手配**する仕組み。
- 手配した会場の**内容を関係部署と共有**する仕組み(ダブルブッキング防止・情報連携)。

### 1-6. 一般項目の入力と見やすい表示
入力した以下のような一般項目を、**見やすい形式で表示**できること:
- 食事の有無
- 請求方法
- 到着時刻
- 料金
- (その他、団体受注で一般的に必要な項目)

**空欄項目の非表示**: 未入力の項目は、帳票・共有ページに**表示しない**(行ごとスキップして詰める)。
例: 宛名は「会社名・団体名・ツアー名」の3項目を持つが、入力があるものだけを帳票に出す。

### 1-7. 案件ステータス(ライフサイクル)
案件は次のステータスで進行する(帳票生成・会場ブロック・カレンダー表示のすべてがこれに連動):

`引合 → 仮予約 → 確定 → 実施済 → 請求済 → 入金済`(+`キャンセル`)

- **仮予約**: 会場を仮押さえ。**重複可・警告表示のみ**(カレンダーに重なりを赤表示)。
- **確定**: 会場を正式ブロック。**同一会場・同一時間帯の重複はシステムが拒否**(ダブルブッキング防止)。人数(確定)の入力が必須になる。
- **請求済以降**: 金額項目はロック(管理者のみ解除可)。

### 1-8. 変更・キャンセルへの追従
団体は変更が常態。次を仕組みで担保する:
- **人数・内容の変更があったら、発行済み帳票に「要再出力」フラグ**を立て、関係部署に通知(例: 人数変更 → 調理発注書が古い、と厨房に分かる)。
- **最終人数確定日**(利用日の n 日前、案件ごとに設定)を持ち、締切前にアラート。
- **キャンセル時**: ステータスを`キャンセル`にすると会場ブロックが解放され、キャンセル料の請求書を同じ明細データから作成できる。

### 1-9. 帳票の版管理
- 帳票の再生成は**上書きではなく新版**(見積 第1版/第2版…)。どの版をいつお客様に出したかを記録。
- 手元調整したExcelは引き継がれない(調整はExcel側の作業と割り切る)。元データが変わったら新版を出す運用。

### 1-10. 権限・承認(シンプルに)
- 閲覧は社内全員。編集は担当者+同部署。**金額の編集と請求書発行は権限者のみ**。
- 変更履歴(誰が・いつ・何を)は全件自動記録。

### 1-11. 入力項目の拡張(後から増やせる)
入力項目は運用しながら追加できる。ただし乱雑にならないよう3つのルールを置く:
1. 追加項目は必ず**既存セクションに帰属**させ、セクション**末尾**に追加(既存の並び順は変えない)。「その他」に溜め込まない。
2. 追加時に**型(選択/自由/数値/日付)・必須/任意・どの帳票に流すか**の3点を必ず定義(出力先のない項目は追加しない)。
3. 運用開始後の「必須」追加は**追加日以降の新規案件のみに適用**(既存案件が一斉に「不足」表示になる事故を防ぐ)。

### 1-12. 出力形式(Excelに統一)
**全帳票(見積書・請求書・領収書・調理発注書・イベント工程表)は Excel を単一の元とする。**

- 理由: **Excelなら誰でも操作でき**、印刷もPDF化もExcelから一発。**PDFを元にするとExcel化できない**ため、元は必ずExcelに統一する。
- 流れ: テンプレートExcelに入力値を**流し込んでダウンロード → 手元で最終調整**(値引き行の追加・備考・レイアウト微修正)→ **Excelから印刷 / PDF保存**。
- お客様向け(見積・請求・領収)はテンプレに**ロゴ**を配置しておき、印刷/PDFでそのまま渡せる完成体裁に。
- **社内共有ページ・カレンダー = Web画面(ライブ)**(ファイル化せず、常に最新を全部署が画面で見る)。

## 2. 成果物ごとの要件(詳細)

### A. 社内共有ページ
- 1案件の基本情報・日程・人数・会場・食事・料金・ステータス・担当を集約。
- フロント/予約/セールス/料飲が同じ情報を見られる(単一の真実)。
- 更新履歴が残り、「誰がいつ何を変えたか」が分かる。

### B. 調理・発注書(料飲/厨房向け)— **Excel**
- 料理内容・コース・品目・**数量(人数連動)**・アレルギー・提供時刻・会場。
- 仕入/発注の指示に使える体裁。人数変更が数量に反映される。
- **Excelテンプレに流し込んでダウンロード** → 厨房で最終調整 → 印刷/PDF。

### C. 見積書 / 請求書 / 領収書(お客様向け)— **Excel**
- 明細(項目・単価・数量・金額)、合計、支払条件。
- **税・料金の内訳に対応**: 消費税率区分(宿泊・飲食)、サービス料の内/外、**入湯税**、**インボイス登録番号**の印字。
- 見積 → 請求 → 領収 を**同じ案件データから連続生成**(再入力なし)。
- 宛名・日付・帳票番号(自動採番)の管理。テンプレに**ロゴ**を配置。
- **Excelで最終調整 → 印刷 / PDF保存**でそのままお客様に渡せる完成体裁。

### D. イベント工程表 — **Excel**
- 当日のタイムライン(時刻・内容・担当・場所)。
- 関係部署が当日の動きを共有できる。
- **Excelテンプレに流し込んでダウンロード** → 運営が最終調整 → 印刷/PDF配布。

## 3. 想定データ項目(入力→各成果物へ供給)

**案件基本**
- 案件名 / 団体名
- 主催・エージェント区分
- 日程(開始〜終了・泊数)
- 人数(見込 / 確定)
- 担当者
- ステータス

**内容**
- 宿泊(部屋タイプ・室数) ← 空き状況参照
- 食事(有無・内容・時刻・会場) → 調理発注書へ
- 宴会・会場(会場名・レイアウト・時間) → 会場手配へ
- 送迎(有無・便・時刻)
- オプション(選択式)

**お金**
- 料金・料金区分 ← 料金マスタ参照
- 見積総額 / 明細
- 請求方法 / 支払条件
- 到着時刻・その他一般項目

→ これらを **必須 / 任意** に分け、選択式にするもの・自由記述にするものを次ステップで確定する。

## 4. 非機能・UX 要件
- **モバイル対応**(現場はPCの前にいない)。
- **見やすい表示**(入力値を帳票・共有ページとして読みやすく)。
- **印刷/PDFが簡単**(ワンクリック)。
- **見落とし防止**(カレンダー・通知)。

## 5. 確定した方針(Sho 回答済み)

1. **料金・空き状況のデータ源**: **当面はアプリ内マスタに手入力**でよい。PMS(Opera等)との自動連携は将来課題。
2. **帳票の体裁**: **読みやすければOK**(既存の固定様式に縛られない)。ただし**後からロゴを入れられる**設計にしておく(ヘッダーにロゴ画像を差し込めるテンプレート)。
3. **会場手配**: **ダブルブッキング判定は必要**。いずれにせよ**カレンダーが必須**(会場×日時で空き/重複を可視化・警告)。
4. **ブロックコード採番**: 会計側の固定ルールは今は無い。ただし **Opera運用向けに「10桁・英数字」のブロックコードを自動生成**したい。入力内容に応じて、人が見て意味を推測できる"気の利いた"コードを生成するのが理想。→ 詳細は §7。

## 6. 会場手配・カレンダー(要件詳細)
- **会場マスタ**: 施設内の会場(宴会場・レストラン等)を登録(名称・定員など)。当面手入力。
- **カレンダー**: 会場 × 日時で予約状況を表示。案件から会場を押さえると、その枠がカレンダーに反映される。
- **ダブルブッキング判定**: 同一会場・同一時間帯に別案件が入ろうとしたら**警告**(または登録をブロック)。
- 手配内容(会場・時間・レイアウト・人数)は関係部署と共有される。

## 7. ブロックコード自動生成(Opera向け・10桁英数字)【案B で確定】
入力内容から、意味が読み取れる10桁の英数字コードを自動生成する。

**目的**: Opera 等での識別に使える、人が見て中身を推測できるコード。

**採用方式 = 案B(略号先頭・読みやすさ重視)**
- 構成: `MMDD`(4桁) + グループ略号4字 + 連番2桁 = **10桁**
- 例) 8/15 TANAKA → `0815TANA01`

**ルール**
- 全て**大文字英数字**、ちょうど**10桁**。
- 先頭4桁は利用開始日の `MMDD`。
- 続く4字はグループ名から自動抽出した略号(ローマ字化 → 母音圧縮/先頭切り出しで4字、4字未満は末尾を `X` 等で補填)、**手修正も可能**。
- 末尾2桁は連番(同一 MMDD+略号 の重複回避)。
- 生成後は**手動編集可**(自動はあくまで初期値)。

> 補足: 案B は `MMDD` 始まりのため年をまたぐと同一文字列があり得る。運用上は連番で区別されるが、年識別が必要になれば先頭を `YYMMDD` に切替可能(その場合は略号を2字に)。まずは案B で進める。

**参考(不採用)**
- 案A: `YYMMDD` + 略号2字 + 連番2桁 → `260815TA01`
- 案C: 種別1字 + `YYMMDD` + 連番3桁 → `W260815001`

## 8. 技術方針(チーム合意メモ)
- **Excel生成はブラウザ側でテンプレ差し込み**(xlsx-template方式: テンプレの `${placeholder}` を置換するだけなので、ロゴ・罫線・印刷設定が完全に無傷)。サーバ側の帳票生成コードは持たない。テンプレ5種は差し替えだけで体裁変更できる置き場に保管。
- **ダブルブッキングは2段構え**: ①保存前チェックで画面警告(カレンダー赤表示) ②DB制約(exclusion constraint)が最終防衛線。制約は**確定案件のみ**対象(仮予約は警告のみ)。会場の時間枠は**準備・撤収込み**で登録。
- **ブロックコード採番はDB関数**(同時入力でも重複しない。unique制約がバックストップ。手修正時も桁・形式チェックが効く)。
- **導出値は入力させない**: 泊数=期間から、見積総額=明細から自動計算(二重入力は必ずズレる)。
- スタック: Astro + Cloudflare Pages + Supabase(Postgres/Auth/Realtime/RLS/Storage)。月額0円で開始可。
